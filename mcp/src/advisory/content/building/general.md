# General container builds

- Pin base-image versions rather than using `latest`. This rule concerns build dependencies; application chart defaults on the main development branch may use `latest`, with immutable references substituted at tag/release time.
- Populate `.dockerignore` for the actual build-context root. Exclude version-control metadata, local dependency directories, host build outputs/binaries, test reports, caches, editor/OS junk, local environment files, credentials, and unrelated files. Prefer a small allowlisted context where practical; retain sources, dependency manifests, lockfiles, and assets needed by the build. Never copy package-registry tokens, npmrc credentials, or SSH keys into an image. Inspect the context when adding or moving a Dockerfile.
- Populate `.gitignore` so generated build artifacts, binaries, dependency directories, caches, coverage/test reports, local configuration/secrets, and editor/OS junk are not committed. Commit reproducibility inputs such as source files, dependency manifests, and lockfiles. Ignore rules do not untrack files already in Git: inspect tracked artifacts and deliberately remove accidental generated files from the index without deleting needed local files. `.gitignore` and `.dockerignore` serve different purposes; maintain both.
- Use multiple build stages and include only required runtime files and dependencies in the final image.
- Where applicable, ship a statically linked executable.
- Treat UID/GID as runtime configuration, ideally supplied by platform admission mutation. Do not use `adduser`, `useradd`, or account/group creation in Dockerfiles, and do not bake an application UID into `USER`. Root-owned application files are fine: make required files readable/executable by the runtime identity, keep the root filesystem read-only, and mount explicit writable scratch/data paths. Do not recursively chown application code to the runtime UID. Avoid restating identity/security fields that admission already owns; inspect the target cluster policy.
- Use JSON exec-form `ENTRYPOINT`/`CMD` to launch the actual application directly, such as `["node", "server.js"]`, `["python", "app.py"]`, or `["/server"]`. It should receive SIGTERM as PID 1 and perform its own bounded shutdown. Avoid shell-form commands; if a setup script is unavoidable, finish it with `exec` so the application replaces the shell.
- Avoid `dumb-init`, `tini`, s6, supervisord, and similar init/supervisor wrappers in newly designed applications. Let Kubernetes restart and scale separate processes. Applications that launch subprocesses must wait for/reap their children and propagate cancellation; an init wrapper does not implement graceful application shutdown.
- Porting a legacy application is an exception: where its process model, fixed identity, or startup behavior cannot reasonably be changed, document the requirement and use the narrowest necessary wrapper or image identity setup. Do not propagate that exception into new service defaults.
- Keep base dependencies aligned between development and production while omitting development-only tools from production.

- Declare all application dependencies and required system libraries or executables explicitly. Do not depend on tools installed on the host.
- Commit dependency lockfiles where supported and use frozen/locked installation during builds; a build must fail if its manifest and lockfile disagree.
- Install dependencies and compile assets during the image build, not during application startup.
- Coding agents should run dependency management, builds, and checks through Skaffold or Docker/Compose. Do not install components on the host for the agent. Edit dependency manifests and lockfiles directly, using lockfile-only package-manager commands when needed, and install application dependencies in the image.
- Keep each environment-variable default in one layer: Go/Python application defaults belong in code, image-specific runtime defaults belong in the Dockerfile, and deployment-specific overrides belong in manifests. Do not repeat code defaults in Dockerfile ENV or image defaults in Kubernetes/Compose configuration. Before reporting missing manifest variables, inspect image ENV and application defaults.
